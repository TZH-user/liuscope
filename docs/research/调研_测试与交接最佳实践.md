# 调研报告：桌面应用「完整测试 → 用户交接」最佳实践

- **调研日期**：2026-10-26（文中所有"查证时间"均为此日期）
- **调研对象**：LiuScope（柳镜）——Python/PySide6 桌面单机工具，PyInstaller 打包 exe，GitHub Release 分发
- **可信度标注**：【官方】官方文档/规范/规范作者；【源码】仓库源码与官方 Issue；【第三方】技术博客/社区讨论/媒体

---

## TL;DR（决策建议）

1. **LiuScope 的测试主体已达标**：离屏 selftest 33 组 + 真机台架（压测/浸泡/交互）≈ 业界"单元/集成 + 少量 E2E"的金字塔形态（Fowler：单元最多、E2E 最少最脆）。**缺口不在数量而在三处**：
   - ① **断言型 UI 自动化缺失**——selftest 是自研冒烟，业界标准件是 `pytest-qt`（qtbot），迁移成本低（selftest 的离屏思路与其一致，可增量改造）；
   - ② **打包产物没有冒烟测试**——PyInstaller onefile 在干净机器上的行为与源码运行不同（隐藏 import、动态库扫描、多 Qt 绑定冲突），必须在 CI 里对 exe 跑一次 `QT_QPA_PLATFORM=offscreen` 启动冒烟；
   - ③ **版本/变更日志未规范化**——采纳 SemVer（已隐式符合）+ Keep a Changelog 格式，把 HANDOFF.md 的"改动清单"沉淀成 CHANGELOG.md。
2. **GitHub Release 已做到业界常规水准**（exe + SHA-256）。补齐三段式 release notes（亮点/修复/已知问题）、`--prerelease` 标记做 beta 渠道、校验和文件随资产上传，即为小团队最佳实践；canary/beta 对单机工具的正确形态就是 **GitHub pre-release tag + 少量种子用户**，无需灰度基础设施。
3. **用户交接清单**：现有 HANDOFF.md（开发者视角）+ 用户手册（用户视角）结构正确；按业界惯例补 4 件：快速上手 5 分钟版、故障排查 FAQ（含"exe 被 Defender 误报"这类打包应用高频问题）、明确卸载方式（单机绿色 exe 的卸载=删文件+删配置目录，要写清楚配置文件在哪）、数据/配置向前兼容说明（gui_settings_qt.ini 升级时如何迁移）。

## 1. 测试金字塔：分层基准

**结论**：单元（纯逻辑，最多最快）→ 集成/服务（模块组合）→ UI/E2E（最少、最脆、最贵）。Fowler 明确"GUI/E2E 应是套件中最小一部分"，常见经验比例 70/20/10（Fowler 本人只强调形状不强调数字）。

- 来源：Martin Fowler《Test Pyramid》 https://martinfowler.com/bliki/TestPyramid.html （2012，【官方】=权威作者原文，查证 2026-10-26）
- 来源：Ham Vocke《The Practical Test Pyramid》 https://martinfowler.com/articles/practical-test-pyramid.html （2018-02-26，【官方】=Fowler 站点长文，查证 2026-10-26）
- 来源：ThoughtWorks《Guidelines for Structuring Automated Tests》 https://www.thoughtworks.com/insights/blog/guidelines-structuring-automated-tests （【第三方】，查证 2026-10-26）

**反模式警示**：倒金字塔/冰淇淋筒（大量手工 E2E + 几乎没有单元测试）是社区总结的头号反模式——变化成本高、脆弱、反馈慢（Software Testing Magazine 对 test pyramid 反模式的归纳，及 Kent C. Dodds 的 Testing Trophy 模型主张加重集成测试占比： https://kentcdodds.com/blog/write-tests-not-too-many-mostly-integration ，【第三方】，查证 2026-10-26）。LiuScope 若继续堆 selftest 组数而不下沉到 `qt/core/` 单元断言，就会滑向"冰淇淋筒"。

**对 LiuScope 的映射**：
| 层 | 业界做法 | LiuScope 现状 |
|---|---|---|
| 单元 | 纯逻辑函数级断言 | `qt/core/`（settings/dsp/control_channel）适合，selftest 已部分覆盖；未用 pytest 参数化 |
| 集成 | 模块组合 + 信号/异步验证 | selftest 33 组（离屏）≈ 此层；AI 控制通道真 socket E2E 待做（HANDOFF 已列） |
| E2E | 少量、覆盖关键用户路径 | 真机台架 qt_stress/qt_soak/qt_interact（人工，COM9）；未自动化、未进 CI |

## 2. PySide6 UI 自动化测试选型

**结论**：用 **pytest-qt 的 `qtbot`** 而不是裸 `QtTest/QTest`。qtbot 封装了 QTest 的鼠标/键盘模拟，并额外提供 `addWidget`（自动清理）、`waitSignal`（异步断言）、`waitUntil`（轮询条件）；Qt 官方文档也不推荐把 QTest 用于 Python 单元测试场景。CI 无头运行用 `QT_QPA_PLATFORM=offscreen`，多绑定共存时用 `QT_API=pyside6` 固定绑定。

- pytest-qt 官方仓库（支持 PySide6）： https://github.com/pytest-dev/pytest-qt （【官方】，查证 2026-10-26）
- pytest-qt 官方文档（qtbot API）： https://pytest-qt.readthedocs.io/en/latest/intro.html （【官方】，查证 2026-10-26）
- Qt Forum 讨论 QTest vs pytest-qt： https://forum.qt.io/topic/151675/ （【第三方】社区，查证 2026-10-26）
- 无头 GUI 测试实践（含 CI）： https://ilmanzo.github.io/post/testing_pyside_gui_applications （2024，【第三方】博客，查证 2026-10-26）
- `QT_QPA_PLATFORM=offscreen` 平台插件： Qt 官方文档 QPA 章节 https://doc.qt.io/qt-6/qpa.html （【官方】，查证 2026-10-26）

**落地建议**：`pip install pytest pytest-qt`，为 `qt/ui/` 的每个页面写 3~8 条关键路径断言（连接状态机、波形页缩放、导出菜单），复用现有离屏环境；selftest.py 保留为发布门禁冒烟，pytest-qt 套件作为日常回归，两者并存不冲突。

**qtbot 典型写法**（依据 pytest-qt 官方文档 API： https://pytest-qt.readthedocs.io/en/latest/intro.html ，【官方】，查证 2026-10-26）：

```python
# qt/tests/test_terminal_page.py
def test_connect_button_state_machine(qtbot, fake_serial):
    page = TerminalPage(serial=fake_serial)   # 串口用假实现注入
    qtbot.addWidget(page)                      # 测试结束自动关闭/销毁
    qtbot.mouseClick(page.btn_connect, Qt.LeftButton)
    qtbot.waitUntil(page.is_connected, timeout=2000)   # 轮询条件而非 sleep
    with qtbot.waitSignal(page.data_received, timeout=1000):  # 信号级异步断言
        fake_serial.emit_rx(b"OK\r\n")
    assert page.tx_rows_right_aligned()
```

要点：①`waitSignal`/`waitUntil` 替代一切固定 `sleep`，这是 pytest-qt 相对手写 QTest 的核心增益；②`addWidget` 防止窗口句柄泄漏导致的连跑失败；③CI 环境变量 `QT_QPA_PLATFORM=offscreen` + `QT_API=pyside6`。

## 3. 打包与发布工程（PyInstaller + GitHub Actions）

**结论**：CI 在 `v*` tag 触发时：干净 venv → 只装 PySide6 相关依赖 → `pyinstaller app.spec` → **对 exe 本体做冒烟**（`QT_QPA_PLATFORM=offscreen` 启动、断言出现就绪标志/退出码 0）→ 上传 artifact 并附到 Release。LiuScope 已有 tag 打包流程，缺的就是"打包后冒烟"这一步。

- PyInstaller+GitHub Actions 多平台打包全流程（含附 artifact 到 release）： https://www.alexjcoleman.me/blog/2023-03-28-building-your-pyinstaller-app-for-multiple-oss-with-github-actions.html （2023-03，【第三方】教程，查证 2026-10-26）
- PyInstaller 6.7.0 起显式禁止一个冻结应用收集多个 Qt 绑定（PySide2/6、PyQt5/6 混装即构建失败）——CI 环境必须干净： https://pyinstaller.org/en/v6.7.0/CHANGES.html （【官方】changelog，查证 2026-10-26）
- 构建不可复现坑：目标 py 未变时 exe 内版本文件不更新 → CI 每次清空 build 目录： https://github.com/pyinstaller/pyinstaller/issues/7338 （【源码】Issue，查证 2026-10-26）
- spec 文件注入版本信息的 CI 做法： https://gist.github.com/JarekParal/24e15de33971674a8c0f9955f6ad15e0 （【第三方】Gist，查证 2026-10-26）
- CI 构建体积膨胀（500MB）的常见原因（脏 venv、未排除项）： reddit r/learnpython 讨论 https://www.reddit.com/r/learnpython/comments/1r1q6aq/ （【第三方】社区，查证 2026-10-26）
- Actions 内无头 UI 测试思路（headless 模式移植到 PySide6 即 offscreen）： https://docs.dev-tools.ai/blog/running-ui-tests-in-github-actions （2022-07，【第三方】博客，查证 2026-10-26）

**Windows 特有交接项**（单机工具高频问题，第三方社区共识，查证 2026-10-26）：PyInstaller onefile 启动慢（自解压到临时目录）要在文档中说明；无签名 exe 会被 SmartScreen/Defender 标记，需在 README/手册提供"仍要运行"指引与 SHA-256 比对方法（LiuScope 已提供 SHA-256，指引用语补齐即可）。

**建议的 CI 打包任务骨架**（综合上述来源，实践建议；LiuScope 现有 ci.yml 之上增量）：

```yaml
# .github/workflows/release.yml 关键步骤（伪代码级）
- run: python -m venv .venv && .venv/Scripts/pip install -r requirements.txt pyinstaller
- run: .venv/Scripts/pyinstaller --noconfirm liuscope.spec     # 每次全新 build 目录（防 #7338）
- run: |                                                        # 打包产物冒烟
      $env:QT_QPA_PLATFORM='offscreen'
      Start-Process dist/liuscope.exe -ArgumentList '--selftest-exit' -Wait
      # 约定：--selftest-exit 完成后以退出码 0/非 0 结束，CI 据此门禁
- run: CertUtil -hashfile dist/liuscope.exe SHA256 > SHA256SUMS.txt
- uses: actions/upload-artifact@v4
- uses: softprops/action-gh-release@v2   # v* tag 时把 exe + SHA256SUMS.txt 附到 Release
```

其中"exe 以 `--selftest-exit` 参数跑离屏自检并回传退出码"是最小改造方案——LiuScope 已有 headless_main.py 与 selftest 基建，只差把入口接到 PyInstaller 冻结上下文里。

## 4. 版本、CHANGELOG 与 beta/canary

**结论**：
- **版本号**：Semantic Versioning（主.次.补丁，破坏性变更升主版本）。LiuScope v1.2.0 命名已符合，把它写成显式纪律即可。官方规范： https://semver.org/lang/zh-CN/ （【官方】，查证 2026-10-26）
- **CHANGELOG**：Keep a Changelog 格式——"为人类而非机器写"，按 Added/Changed/Deprecated/Removed/Fixed/Security 分节，每个版本带日期，Unreleased 区常开。官方规范： https://keepachangelog.com/zh-CN/1.1.0/ （【官方】，查证 2026-10-26）。自动化工具有 semantic-release/standard-version，但小团队手写 + Conventional Commits 提交习惯收益更高、零配置。
- **beta/canary**：canary/灰度的本义是"先放给小流量、观察指标、再全量"（服务端形态，见 LaunchDarkly https://launchdarkly.com/blog/how-to-integrate-canary-releases 、BMC https://www.bmc.com/blogs/canary-deployment-release 、Flagsmith https://www.flagsmith.com/blog/canary-deployment ，均【第三方】，查证 2026-10-26）。**单机桌面工具的对应物**：GitHub Release 勾选 `--prerelease`（tag 如 v1.3.0-beta.1），种子用户群试 → 问题收敛后发正式版。不测试线上指标，收集的是 issue 反馈，因此"观察期清单"要预先写进 prerelease 说明（想验证什么、反馈渠道、回滚=装回上一版 exe）。

**prerelease 正文模板**（实践建议，综合 GitHub 官方 releases 文档结构）：

```markdown
## v1.3.0-beta.1（预发布，请勿用于关键工作）
本 beta 想验证：① 新增 XXX 在 Windows 10/11 的兼容性 ② 投屏功能在真机的延迟
已知问题：见文末。反馈：请开 Issue 并附 汉化日志 logs/ + 版本号。
回滚：直接下载上一版 v1.2.0 的 liuscope.exe 覆盖即可（配置文件互相兼容）。
SHA-256：<hash>
```

beta 转正的收敛条件（实践建议）：无新增 critical/high issue、观察用户 ≥3 人 ≥3 天、beta 期修复项全部经 selftest + 真机台架复验。

## 5. GitHub Release 最佳实践

**结论**：Release notes 推荐三段式「新特性亮点 / Bug 修复 / 已知问题(含升级注意事项)」+ 资产（exe、SHA-256SUMS.txt）。GitHub 官方支持自动生成 release notes（基于 PR 标签），小团队可先生成再人工改写。

- Releases 官方概念与操作： https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases （【官方】，查证 2026-10-26）
- 自动生成 release notes（.github/release.yml 配置分类）： https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes （【官方】，查证 2026-10-26）
- 校验和随资产发布的行业样板：GoReleaser 内置 checksum 管道（`checksum: algorithm: sha256`，产出 checksums.txt 一并上传）： https://goreleaser.com/customization/checksum/ 与官方示例仓库 https://github.com/goreleaser/example-sign-with-env/blob/main/.goreleaser.yaml （【官方】工具文档，查证 2026-10-26）。LiuScope 手工等价物：`sha256sum dist/liuscope.exe > SHA256SUMS.txt` 上传。

**Release notes 三段式模板**（实践建议；"已知问题"段落是业界区分业余/专业发布的标志项，直接把 HANDOFF 的"已知限制"翻译成用户语言放入）：

```markdown
# LiuScope v1.3.0
## ✨ 新特性
- 投屏：经网线连接 LubanCat，端到端延迟目标 <80ms（详见用户手册 §X）
## 🛠 修复
- 终端页断开重连后按钮状态不同步（#xx）
## ⚠️ 已知问题与升级注意
- CubeProgrammer CLI 中文控制台 Description 字段显示 `?`（CLI 自身管道码页所致）
- 升级无需迁移配置；如遇异常删除 gui_settings_qt.ini 重置
SHA-256 见附件 SHA256SUMS.txt；校验方法：`certutil -hashfile liuscope.exe SHA256`
```

**资产校验和标准动作**（发布时两条命令，Windows/Linux 各一）：

## 6. 用户交接文档（用户视角）

业界对"交接文档"的共识结构（综合 GitHub 官方 releases/repositories 文档与上述发布工程实践，【官方】+【第三方】，查证 2026-10-26）：
1. **快速上手**：下载 → 校验 SHA-256 → 运行 → 完成第一个任务，≤5 分钟路径，放 README 顶部或 Release 正文；
2. **系统要求**：Win10+、位数、是否需要 VC 运行库（PyInstaller 通常自带但需声明）；
3. **配置与数据**：配置文件位置（LiuScope：`gui_settings_qt.ini`）、升级是否兼容、如何重置；
4. **故障排查 FAQ**：启动失败、SmartScreen 拦截、杀软误报、串口被占用（CH340/CP210x 驱动）、日志位置（`logs/`）；
5. **卸载**：单机绿色版 = 删除 exe + 删除配置/日志目录，写明具体路径；
6. **反馈渠道**：Issues 链接 + 需要附上的信息（版本号、日志、复现步骤）。

LiuScope 现状：用户手册 v1.2 已有，缺"卸载与配置位置"与"SmartScreen/误报应对"两节；HANDOFF.md 是开发者交接（质量很好），两者定位不同，建议在 HANDOFF.md 顶部加一行"用户请看 docs/用户手册"的互链。

**用户手册增补骨架**（针对 LiuScope 单机绿色 exe 形态的具体化，实践建议）：

```markdown
## 快速上手（5 分钟）
1. 下载 Release 中 liuscope.exe 与 SHA256SUMS.txt
2. certutil -hashfile liuscope.exe SHA256 与附件比对
3. 双击运行（首次启动 SmartScreen 提示：点"更多信息→仍要运行"）
4. 插入串口设备 → 终端页选择 COM 口 → 连接

## 配置与数据
- 配置：gui_settings_qt.ini（与 exe 同目录或 %APPDATA%，以实际为准）
- 日志：logs/
- 升级：新版直接覆盖，配置向前兼容；重置=删除该 ini

## 卸载
- 删除 liuscope.exe + gui_settings_qt.ini + logs/（不写注册表，无残留）

## 故障排查
| 现象 | 处置 |
|---|---|
| 双击无反应/报缺 DLL | 装 VC++ 运行库；查 logs/ |
| SmartScreen/杀软拦截 | 比对 SHA-256 后加白名单 |
| 找不到 COM 口 | 装 CH340/CP210x 驱动；设备管理器确认 |
| 串口被占用 | 关闭其他占用程序（含另一个 LiuScope 实例） |
| 启动慢（3~10s） | onefile 自解压特性，非卡死 |
```
